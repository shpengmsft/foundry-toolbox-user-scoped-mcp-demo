# Setup guide: user-scoped MCP with fake OAuth

This guide configures the demo-only OAuth provider and remote MCP server so a
Microsoft Foundry Toolbox can receive different tool catalogs for different
test identities.

The fake provider is intended for demos and automation tests only. It exercises
the OAuth authorization-code, token refresh, bearer-token forwarding, and MCP
authorization paths without requiring an Entra client secret.

## What the setup demonstrates

One MCP endpoint returns a different successful `tools/list` response according
to the `oid` in the access token:

| Test identity | Test `oid` | Visible role-specific tools |
|---|---|---|
| Demo Engineer | `11111111-1111-1111-1111-111111111111` | Incident, deployment, and incident-mitigation tools |
| Demo Finance User | `22222222-2222-2222-2222-222222222222` | Budget, cost-center, and spend-mitigation tools |
| Demo Administrator | `33333333-3333-3333-3333-333333333333` | All Engineer and Finance tools |

All identities also receive `get_current_user`.

The fake OAuth provider and MCP server run in the same FastAPI application:

```text
Foundry user
    |
    | OAuth authorization and consent
    v
/oauth/authorize -> /oauth/token
    |
    | signed test JWT containing oid
    v
Foundry Toolbox -> /mcp -> role-specific tools/list and tools/call
```

## 2. Run the fake provider locally

Set the test configuration:

```powershell
$env:AUTH_MODE = "fake_oauth"
$env:FAKE_OAUTH_ISSUER = "http://localhost:8000"
$env:FAKE_OAUTH_AUDIENCE = "user-scoped-mcp-demo"
$env:FAKE_OAUTH_CLIENT_ID = "foundry-test-client"
$env:FAKE_OAUTH_REDIRECT_URIS = "http://localhost:8400/callback"
$env:SERVER_HOST = "127.0.0.1"

.\.venv\Scripts\user-scoped-mcp
```

Verify the service:

```powershell
Invoke-RestMethod "http://localhost:8000/health"
Invoke-RestMethod "http://localhost:8000/.well-known/openid-configuration"
```

Open the following URL in a browser to display the identity picker:

```text
http://localhost:8000/oauth/authorize?response_type=code&client_id=foundry-test-client&redirect_uri=http%3A%2F%2Flocalhost%3A8400%2Fcallback&scope=mcp.access%20offline_access&state=local-test
```

The final redirect fails if no application is listening on port 8400. That is
expected for this manual check; the redirect URL contains the one-time
authorization code.

## 3. Deploy or update Azure Container Apps

### Calculate the issuer

The OAuth issuer must exactly match the public origin used by Foundry. When
reusing an existing Container Apps environment:

```powershell
$resourceGroup = "rg-shpeng-sc"
$environment = "mcpdiag-shpeng-aca-env"
$containerApp = "shpeng-mcp-fake-oauth"

$defaultDomain = az containerapp env show `
  --resource-group $resourceGroup `
  --name $environment `
  --query properties.defaultDomain `
  --output tsv

$issuer = "https://$containerApp.$defaultDomain"
$issuer
```

For the current environment, `$issuer` is:

```text
https://shpeng-mcp-fake-oauth.thankfuldune-62c51cc5.swedencentral.azurecontainerapps.io
```

### Initial deployment

Foundry does not reveal its callback URL until the OAuth connection is created.
Use a placeholder redirect for the initial deployment:

```powershell
.\scripts\deploy-container-app.ps1 `
  -ResourceGroup "rg-shpeng-sc" `
  -Location "swedencentral" `
  -ContainerAppName "shpeng-mcp-fake-oauth" `
  -AuthMode fake_oauth `
  -FakeOAuthIssuer $issuer `
  -FakeOAuthClientId "foundry-test-client" `
  -FakeOAuthRedirectUris "https://automation.invalid/callback" `
  -RegistryName "ca6ef7d870dbacr" `
  -ContainerAppsEnvironment "mcpdiag-shpeng-aca-env" `
  -ImageTag "fake-oauth-initial"
```

Use a new `ImageTag` for each deployment. An image change guarantees that the
Container App starts a process with the latest code and environment settings.

## 4. Create the Foundry OAuth connection

In the Foundry project:

1. Open the project management or connections experience.
2. Create a connection for a remote MCP server.
3. Select **OAuth identity passthrough** or the equivalent `oauth2`
   authentication option.
4. Enter the following values.

| Foundry field | Value |
|---|---|
| MCP endpoint/target | `<issuer>/mcp` |
| Client ID | `foundry-test-client` |
| Client secret | Leave empty |
| Auth URL | `<issuer>/oauth/authorize` |
| Token URL | `<issuer>/oauth/token` |
| Refresh URL | `<issuer>/oauth/token` |
| Scopes | `mcp.access offline_access` |

OAuth client IDs are strings. The fake provider's default client ID is the
literal string `foundry-test-client`; it does not need to be a UUID.

If the portal requires a nonempty client-secret value, enter a test-only
placeholder such as `not-used`. Any string works because the fake provider
does not validate or use the client secret. Leave it empty when the portal
allows that. Never reuse a real credential.

Save the connection. Foundry then displays or generates its OAuth redirect URL.
Copy the complete URL exactly, including path and case.

## 5. Allow the Foundry redirect URL

Redeploy with the generated redirect URL:

```powershell
$foundryRedirectUri = "<paste-the-complete-foundry-redirect-url>"

.\scripts\deploy-container-app.ps1 `
  -ResourceGroup "rg-shpeng-sc" `
  -Location "swedencentral" `
  -ContainerAppName "shpeng-mcp-fake-oauth" `
  -AuthMode fake_oauth `
  -FakeOAuthIssuer $issuer `
  -FakeOAuthClientId "foundry-test-client" `
  -FakeOAuthRedirectUris $foundryRedirectUri `
  -RegistryName "ca6ef7d870dbacr" `
  -ContainerAppsEnvironment "mcpdiag-shpeng-aca-env" `
  -ImageTag "fake-oauth-foundry-callback"
```

To allow multiple Foundry projects or automation callbacks, pass a
comma-separated list:

```powershell
-FakeOAuthRedirectUris "https://callback-one.example/path,https://callback-two.example/path"
```

The provider uses exact matching and rejects unregistered redirects.

Confirm the deployed issuer:

```powershell
Invoke-RestMethod "$issuer/.well-known/openid-configuration" |
  Select-Object issuer, authorization_endpoint, token_endpoint
```

The returned `issuer` must exactly equal `$issuer`.

## 6. Add the MCP connection to one Toolbox

1. Create or open a Toolbox.
2. Add one remote MCP tool.
3. Set the server URL to `<issuer>/mcp`.
4. Select the OAuth project connection created above.
5. Publish a Toolbox version.
6. Attach that same Toolbox version to the test agent.

Do not create different Toolbox versions for Engineer and Finance. The purpose
of the demo is to prove that one Toolbox and one MCP endpoint can return
different tool catalogs according to the token identity.

## 7. Run the manual demo

Use two separate Foundry users or browser sessions so Foundry maintains
separate per-user OAuth grants.

### Engineer session

1. Submit a request that requires the MCP tool.
2. Open the OAuth consent link returned by Foundry.
3. Select **Demo Engineer**.
4. Resume or repeat the agent request.

### Finance session

Use the same prompt in both sessions:

## 8. Automation guidance

The authorization endpoint accepts a test-only `test_user` parameter:

```text
test_user=engineer
test_user=finance
test_user=admin
```

For browser automation:

1. Capture the `oauth_consent_request` and its `consent_link`.
2. Open the consent link.
3. Select the required identity, or append the required `test_user` query
   parameter before navigating.
4. Follow the redirect back to Foundry.
5. Continue the previous response or retry the agent request.
6. Assert the discovered tools and selected tool calls.

Recommended assertions:

| Scenario | Assertion |
|---|---|
| Engineer authorization | Engineer-only tools are present; Finance-only tools are absent |
| Finance authorization | Finance-only tools are present; Engineer-only tools are absent |
| Same prompt | Each identity selects its own mitigation workflow |
| Refresh | A request after access-token expiry succeeds using the refreshed token |
| Isolation | One user's selected fake identity does not change another user's tool catalog |
| Invalid redirect | Authorization returns HTTP 400 |
| Missing scope | Authorization returns HTTP 400 |

For provider-level automation without Foundry, run:

```powershell
.\.venv\Scripts\python -m pytest -q
```

## 9. Troubleshooting

### Foundry reports an OAuth redirect or callback error

- Copy the redirect URL generated by Foundry exactly.
- Add it to `FAKE_OAUTH_REDIRECT_URIS`.
- Redeploy with a new image tag.
- Do not add or remove a trailing slash unless Foundry's URL contains it.

### Authorization returns `redirect_uri is not allowed`

The incoming `redirect_uri` does not exactly match the configured allowlist.
Inspect the Foundry-generated redirect and redeploy with that value.

### Authorization returns `Required scope is missing: mcp.access`

Set the Foundry scopes field to:

```text
mcp.access offline_access
```

Scopes are separated by a single space, not a comma.

### Token exchange returns `invalid_client`

Set Client ID to exactly:

```text
foundry-test-client
```

If a different client ID is required, redeploy with the same value in
`-FakeOAuthClientId`.

### MCP returns HTTP 401

- Confirm Foundry is sending the OAuth access token to the `/mcp` endpoint.
- Confirm the discovery issuer equals the external HTTPS origin.
- Complete authorization again after a redeployment because signing keys are
  regenerated whenever the process restarts.

### Existing grants stop working after deployment

This is expected. The provider creates an in-memory RSA signing key at startup.
Tokens issued before a restart no longer validate. Repeat the consent flow.

### Azure CLI fails while streaming build logs on Windows

Supply both `-RegistryName` and `-ContainerAppsEnvironment`. The deployment
script then uses `az acr build --no-logs`.

### Tool Search returns the same candidates

- Confirm the two Foundry callers have separate OAuth grants.
- Call `get_current_user` and verify the returned test `oid` and role.
- Confirm one user selected Engineer and the other selected Finance.
- Confirm both sessions use the same published Toolbox version.

## Security boundaries

This provider is intentionally unsuitable for production:

- Anyone who reaches the authorization endpoint can select any test identity.
- Test identities are not authenticated.
- Grants and authorization codes are stored only in memory.
- Signing keys rotate on every process restart.
- There is no logout, revocation, user store, or audit-grade identity proof.
- A placeholder client secret is ignored.

Use the provider only in an isolated test environment with synthetic data. The
result proves Foundry OAuth passthrough mechanics and identity-dependent MCP
discovery; it does not prove Microsoft Entra authentication.
